# AgentCollar relay — дизайн v1

Дата: 2026-10-04 · Статус: черновик на ревью

## 1. Зачем

Брокер становится **публичным продуктом**: им пользуются другие люди, каждый со своими агентами,
и одобряют мандаты в Telegram. Сейчас бот настраивается через `.env` — это годится только
для одного человека, умеющего работать с @BotFather. Нужна архитектура, где пользователь
за минуту привязывает свой брокер к **одному официальному боту** AgentCollar.

**Готово, когда:** новый пользователь запускает брокер, выполняет `npm run pair`,
жмёт Start в боте — и дальше получает запросы мандатов в Telegram со своего компьютера,
при этом его Google-токены, mandate tokens и письма никогда не покидают его компьютер.

## 2. Принятые решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Где работают агенты | И локально, и в облаке — **по этапам**: v1 только локальные, облачные в v2 | Выпустить честную v1 быстрее; облачных делать сразу с E2E |
| 2 | Где хранятся доступы к приложениям | **Только на компьютере пользователя** (local-first) | Главное обещание продукта; меньше риска и ответственности |
| 3 | Какой бот | **Один официальный бот + relay-сервер** | Настройка за минуту; relay всё равно нужен для v2 |
| 4 | Трафик облачных агентов | **v2, с end-to-end шифрованием**; в v1 его нет | Relay не должен видеть письма |
| 5 | Отказы и поломки | **Fail closed**: любая поломка уменьшает доступ, никогда не одобряет сама | Безопасность важнее удобства |

Режим «свой бот через `.env`» (текущий `telegram.ts`) **остаётся** как вариант без relay.

## 3. Не входит в v1

- Облачные агенты и end-to-end шифрование (v2).
- Несколько одобряющих людей на один брокер.
- Веб-панель, установщик, упаковка в приложение (запуск — через `npm run ...`).
- Выбор хостинга для relay — решается перед публичным запуском, отдельно. Вся v1 разрабатывается
  и проверяется с relay на `localhost`.

## 4. Компоненты

```
  Компьютер пользователя                      Интернет (AgentCollar)         Телефон
 ┌───────────────────────────────┐          ┌───────────────────┐        ┌───────────┐
 │ Агенты ──HTTP──► Брокер       │ outbound │  Relay            │  Bot   │ Telegram  │
 │                  127.0.0.1    │═WebSocket═► token бота,      │◄─API──►│ официаль- │
 │                  │            │          │  таблица привязок │        │ ный бот   │
 │      Google-токены, audit log │          └───────────────────┘        └───────────┘
 │      ключ брокера — только здесь                                         
 └───────────────────────────────┘
```

### 4.1 Брокер (`broker/`, есть сейчас + новое)

- Всё существующее не меняется: `check()`, audit log, HTTP только на `127.0.0.1`, защита от браузеров.
- **Новое:**
  - `src/identity.ts` — при первом запуске создаёт пару ключей **Ed25519** (встроенный `node:crypto`)
    и хранит её в `broker/data/identity.json` (папка `data/` уже в `.gitignore`, права файла `600`).
    Перенос в macOS Keychain — вместе с фазой 4 (Google OAuth), там же, где refresh token.
  - `src/relay-client.ts` — держит WebSocket к relay, переподключается, отправляет запросы
    на одобрение, получает решения и передаёт их в существующую `decide()`.
  - `src/pair.ts` + команда `npm run pair` / `npm run unpair`.
  - Команда `npm run revoke -- <id>` — локальный kill switch, работает без relay.
  - Таймаут pending: мандат без решения через **10 минут** автоматически становится `denied`.
- Выбор канала одобрения при старте сервера: есть привязка к relay → relay; иначе есть
  `TELEGRAM_BOT_TOKEN` → свой бот; иначе → терминал.

### 4.2 Relay (`relay/`, новая папка со своим `package.json`)

- Держит token официального бота (в своём `.env` на сервере, никогда в репо).
- Говорит с Telegram через long polling (как текущий `telegram.ts`).
- Принимает WebSocket-соединения от брокеров.
- **Хранит на диске только** таблицу `brokers`: `broker_id`, `public_key`, `name`,
  `telegram_user_id`, `created_at` (SQLite). Всё остальное — в памяти:
  pairing-коды (10 мин), ожидающие запросы, недоставленные решения (10 мин).
- Не знает и не может узнать: mandate tokens, Google-токены, письма, audit log.

### 4.3 Что проходит через relay

Только: id мандата, имя агента, текст задачи, список действий, срок, лимит, имя брокера,
решение человека. Текст от агента relay показывает так же, как сейчас брокер: одной строкой,
после настоящих фактов, в кавычках (функции `oneLine`/`describe` переиспользуются).

## 5. Протоколы

Все сообщения WebSocket — JSON-объекты с полем `type`. Соединение только по `wss://`
(TLS) в продакшене; на `localhost` при разработке — `ws://`.

### 5.1 Аутентификация брокера (при каждом подключении)

1. Брокер подключается и отправляет `{type: "hello", brokerId}` (или `{type: "register", publicKey, name}`, если ещё не зарегистрирован).
2. Relay отвечает `{type: "challenge", nonce}` — 32 случайных байта.
3. Брокер подписывает `nonce` своим приватным ключом: `{type: "auth", signature}`.
4. Relay проверяет подпись по сохранённому `public_key`. Не сошлось → закрывает соединение.

После этого вся сессия считается аутентифицированной: отдельно подписывать каждое сообщение
не нужно (уточнение к части 2 обсуждения: «подписано ключом брокера» = подписан вход в сессию).

### 5.2 Привязка

1. `npm run pair` → брокер (после `register` + `auth`) просит `{type: "pair_start"}`.
2. Relay создаёт код из 8 символов без похожих букв (например `7F3K92QD`), живёт 10 минут,
   одноразовый, отвечает `{type: "pair_code", code, link}`; `link` = `https://t.me/<бот>?start=<code>`.
3. Брокер печатает код и ссылку. Человек открывает ссылку → Telegram шлёт боту `/start <code>`.
4. Relay находит код, записывает `telegram_user_id` к брокеру, удаляет код.
   Бот: «✅ Брокер «<name>» привязан». Брокеру: `{type: "paired", telegramName}`.
5. Если брокер уже был привязан к другому аккаунту — привязка заменяется, и **старому**
   аккаунту бот пишет «Брокер «<name>» перепривязан к другому аккаунту».
6. Ограничение: не больше 5 неверных кодов в минуту с одного Telegram-аккаунта.

### 5.3 Одобрение

1. Агент → брокер: `POST /mandates` (без изменений).
2. Брокер → relay: `{type: "approval_request", mandateId, agent, task, actions, expiresInSeconds, limit}`.
3. Relay → Telegram: сообщение привязанному `telegram_user_id`, кнопки с
   `callback_data = "<approve|deny|revoke>:<brokerId>:<mandateId>"` (после одобрения остаётся кнопка «🛑 Отозвать»).
4. Нажатие: relay проверяет, что `from.id` = `telegram_user_id` этого `brokerId`. Иначе — «Нет доступа».
5. Relay → брокер: `{type: "decision", mandateId, decision}`.
6. Брокер вызывает `decide()`; она применяет решение только к `pending`
   (для `revoke` — к любому существующему). Брокер отвечает
   `{type: "mandate_update", mandateId, status}`, relay обновляет сообщение и кнопки.
7. Когда статус меняется на самом брокере (таймаут 10 минут, локальный revoke) — тоже
   `mandate_update`, чтобы сообщение в Telegram не врало.

### 5.4 Отвязка

`/unpair` в боте или `npm run unpair` → relay удаляет `telegram_user_id` у брокера,
обе стороны получают подтверждение. Брокер переходит на одобрение в терминале.

## 6. Ошибки и поломки (fail closed)

| Ситуация | Поведение |
|---|---|
| Брокер не в сети, человек нажал кнопку | Relay держит решение 10 мин, доставляет при переподключении; иначе сообщение → «⚠️ Брокер не в сети, решение не доставлено» |
| Relay недоступен | Брокер переподключается: 1, 2, 4… до 60 с. Новые запросы — в терминал. Без одобрения доступа нет |
| Kill switch без интернета | `npm run revoke -- <id>` и `POST /mandates/:id/revoke` работают всегда, локально |
| Никто не ответил 10 мин | Мандат → `denied`, сообщение → «⌛ Время вышло» |
| Пользователь заблокировал бота | Telegram вернёт ошибку → relay шлёт брокеру `{type: "human_unreachable", mandateId}` → брокер просит в терминале и пишет в audit log |
| Два компьютера у одного человека | Каждый брокер привязывается отдельно, своё имя в каждом запросе |
| Relay перезапустился | Привязки в SQLite сохранились; ожидающие запросы брокер переотправляет после `auth` |
| Повтор старого `decision` | Ничего не меняет: решение принимается только для `pending` |
| Спам запросами от брокера | Relay: не больше 30 `approval_request` в минуту на брокер, сверх — отказ |

## 7. Безопасность: что будет, если взломают relay

- Злоумышленник может **подделать «Одобрить»** для мандата, который уже запросил агент
  на компьютере пользователя. Создать мандат или вызвать брокер он не может (`127.0.0.1`).
- Может **глушить** запросы — неприятно, но безопасно (fail closed).
- Не получит: mandate tokens, Google-токены, письма, audit log, приватные ключи брокеров.
- Захват официального бота (утечка его token) ≈ взлом relay: тот же список.

Сознательно принятый риск v1. В v2 можно добавить вторую защиту: подтверждение опасных
действий (`*.send`) кодом прямо на компьютере.

## 8. Зависимости — нужно одобрение перед планом

| Что | Вариант | Зачем |
|---|---|---|
| WebSocket-клиент в брокере | встроенный `WebSocket` в Node 22 | без зависимостей |
| WebSocket-сервер в relay | пакет **`ws`** | в Node нет встроенного WebSocket-сервера |
| База в relay | встроенный `node:sqlite` | без зависимостей; пока помечен experimental (печатает предупреждение) |
| Ключи и подписи | встроенный `node:crypto` (Ed25519) | без зависимостей |

## 9. Тестирование

- Relay — с поддельным Telegram API (подмена `fetch`), как уже проверялись кнопки.
- Брокер — с поддельным relay (маленький WebSocket-сервер в тесте).
- Сценарии атак: чужой `from.id`, неверный pairing-код, просроченный код, неверная подпись
  при `auth`, повтор `decision`, `decision` для чужого `brokerId`.
- End-to-end: relay на `localhost`, настоящий бот, `npm run pair` → `npm run agent`.

## 10. Порядок работ (детали — в плане)

Рекомендация: делать relay **до** фазы 4 (настоящий Gmail) — они не зависят друг от друга,
а relay меняет то, как пользователь впервые знакомится с продуктом.

1. `identity.ts` + каркас `relay/` + аутентификация по challenge.
2. Привязка (`pair` / `unpair`).
3. Одобрение через relay + `mandate_update`.
4. Поломки: переподключение, таймаут pending, недоставленные решения, `human_unreachable`.
5. End-to-end с настоящим ботом на `localhost`.
